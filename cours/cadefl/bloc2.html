01 — Pourquoi un Bloc 2 ?

À la fin du Bloc 1, tu sais déjà décrire le flux : layer map légère, DFD de la soumission d'un claim et BPMN du processus d'approbation. Mais le cours pose un problème de gouvernance : un diagramme de processus seul n'explique pas comment métier, applications et technologie s'emboîtent.

Model

Produire une vue ArchiMate couvrant Business, Application et Technology.

Refine

Transformer le BPMN du Bloc 1 en modèle à responsabilités explicites.

Label

Utiliser COBIT, ITIL et TOGAF comme vocabulaire d'annotation, sans refaire INLAGO.

Present

Construire une carte compréhensible par un CODIR sans traduction technique.

Le changement de perspective : le Bloc 1 répond surtout « comment le SI fonctionne-t-il ? ». Le Bloc 2 ajoute « comment représenter cette réalité pour qu'un décideur voie la structure, les responsabilités et les points de passage critiques ? »

Piège classique : ces notations ne se remplacent pas. Elles donnent des vues complémentaires du même SI. Le Bloc 2 ajoute ArchiMate parce que ni le DFD ni le BPMN ne suffisent à montrer la structure Business → Application → Technology sur une seule vue.
Support CADEFL · ArchiMate

03 — ArchiMate : la grille de lecture

Le support réduit volontairement l'apprentissage à deux axes simples : 3 layers pour savoir où placer un élément et 3 shape families pour savoir quel rôle conceptuel il joue.

A. Les trois couches

Business

Ce qui relève du métier : acteurs/rôles, comportements et objets métier.

Application

Les composants et services applicatifs qui supportent le métier.

Technology

Les nœuds et infrastructures qui supportent les applications.

B. Les trois familles

FamilleQuestionExemples explicitement donnés
Active structureWho / what performs behaviour?Actor · role · component · node
BehaviourWhat happens?Process · function · service
Passive structureWhat is acted upon?Business object · data object
Technique de classement : commence par demander « quelle couche ? », puis « actif, comportement ou passif ? ». Le support insiste : la position exacte dans le dessin peut se discuter ; la couche conceptuelle, elle, doit être justifiable.

C. Realisation : donner du sens entre les couches

Le challenge demande de tracer les relations de realisation entre les couches. L'objectif pédagogique est de ne pas produire trois inventaires horizontaux indépendants : la vue doit montrer comment les éléments d'une couche permettent ou réalisent ceux d'une autre.

MedLink · exercice du Bloc 2

04 — Les 12 pièces MedLink

Le cours donne douze éléments à classer. Il signale lui-même deux nuances importantes : Claim Data est de la passive structure et Handle Member Claim du behaviour. Autrement dit, « layer » et « shape family » sont deux axes à ne pas confondre.

Business

Claims Adjuster · Cloud Squad Lead · Handle Member Claim · Claim Data (record) selon la nature métier retenue dans l'exercice.

Application

Claims API · Provider Portal · Auto-Scoring Service · Member Registry · Policy Ledger.

Technology

Mainframe · Cloud Cluster · Legacy Batch Job, avec une attention particulière à la distinction infrastructure/comportement technique.

Important pour réviser : le support fournit la liste et demande aux équipes de la classer, mais l'extrait textuel ne donne pas une table de correction exhaustive élément par élément. Les regroupements ci-dessus servent de grille de travail ; retiens surtout la méthode de justification et les catégories explicitement enseignées.
Questions à te poser pour chaque élément

Est-ce un acteur/rôle métier ? Une application ou un service applicatif ? Un nœud/infrastructure ? Est-ce quelque chose qui agit, quelque chose qui se produit, ou quelque chose sur lequel on agit ? Quelle relation permet de remonter ou descendre vers une autre couche ?

Support CADEFL · BPMN refinement

05 — BPMN raffiné : rendre l'ownership visible

Pools vs lanes

Pool

Le support pose la règle de travail : un pool par organisation. Dans MedLink, Cloud et Legacy obtiennent chacun leur pool pour rendre l'ownership visible immédiatement.

Lane

Une lane représente un rôle ou système à l'intérieur d'un pool lorsque les participants restent dans la même organisation.

Trois éléments à maîtriser

Parallel Gateway

Deux branches s'exécutent simultanément ; les deux doivent terminer avant de continuer. Losange avec « + ».

Message Flow

Flèche en pointillés entre pools : information qui traverse une frontière organisationnelle, distincte d'un sequence flow.

Sub-process

Boîte repliée avec petit « + » : cache le détail inutile au board, tout en permettant de le développer dans une annexe technique.

Le modèle MedLink raffiné

Pool Cloud
Submit & Auto-score → Auto-approve & notify
- - - →
Pool Legacy
Manual Review → Update Ledger
Ce qui change par rapport au Bloc 1 : deux pools au lieu de responsabilités mélangées ; un message flow marque précisément le handoff Cloud → Legacy ; pour le board, les noms des pools et le point de passage sont plus importants que chaque étape interne.

06 — Savoir reconnaître un mauvais BPMN

Le cours présente volontairement un diagramme de junior analyst avec au moins cinq problèmes. Les indices fournis sont eux-mêmes une checklist de revue.

1 · Tout dans une seule lane

« MedLink (everything, one lane) » masque la séparation Cloud/Legacy et donc l'ownership recherché.

2 · Mauvais type de flux

Un sequence flow traverse vers Legacy alors que le cours attend un message flow entre les deux pools.

3 · Gateway sans raison

Un parallel gateway est placé alors qu'il n'y a rien à paralléliser : un symbole doit « mériter sa place ».

4 · Labels trop techniques

Invoke REST endpoint /v2/score ou PL/I batch routine CLM_VALIDATE_v4.2 sont des détails inadaptés à un board pack.

5e problème à rechercher : le support indique également « Update ledger (no handoff shown) ». Le diagramme échoue donc à rendre explicitement visible le passage critique vers Legacy, précisément ce que le CODIR doit comprendre.

Checklist de debug issue du cours

  • Les organisations sont-elles correctement regroupées ?
  • Chaque flèche est-elle du bon type — solide ou pointillée ?
  • Chaque gateway a-t-elle une vraie fonction ?
  • Chaque label serait-il compris par un CODIR ?
  • Le handoff critique est-il visible ?
Support CADEFL · CODIR Test

07 — Concevoir pour un CODIR

Le message du cours est volontairement brutal : une documentation peut être techniquement exacte et pourtant être inutilisable pour décider.

Feedback du board : il ne veut pas une architecture technique exhaustive. Il veut savoir qui possède quoi et où sont les handoffs critiques.

Le test des 20 secondes

Le support affiche volontairement des détails comme claim_id VARCHAR(24) PK, AUTH_SVC.validate(token), une fenêtre CRON, un événement API ou un dataset mainframe, puis demande : qu'a réellement compris le CIO ? La leçon n'est pas que ces données sont inutiles, mais qu'elles ne répondent pas à la question du board.

Le filtre de simplification

1
Réécrire tout label que le CODIR ne reconnaîtrait pas
→
2
Couper ce qui ne change pas une décision du board
→
3
Garder : what is it? who owns it? why does it matter?
Principe-clé du Bloc 2 : la qualité d'une vue CODIR dépend aussi de ce qu'elle retire. La dernière slide le formule explicitement : « A CODIR judges your map on what it cuts, not what it includes. »

08 — Labels de gouvernance : juste assez

Le Bloc 2 ne réenseigne pas COBIT, ITIL ou TOGAF. Le support dit explicitement que la profondeur appartient à INLAGO ; ici, ces référentiels deviennent des annotations sur la carte.

Project Increment · D2

09 — Ce que tu dois produire

Tout ce qui est construit pendant le Bloc 2 devient un package propre. Une contrainte est explicite : chaque élément doit tracer vers quelque chose déjà présent dans la carte du Bloc 1 — aucun nouveau scope.

1 · ArchiMate View

Business / Application / Technology pour la claims capability, avec realisation links.

2 · Refined BPMN

Deux pools et un message flow marquant le handoff legacy/cloud.

3 · Vocabulary Labels

2–3 éléments annotés avec le framework de gouvernance associé.

Format : un fichier source .drawio + un PDF exporté, soumis par équipe, attendu au début du Bloc 3. Il s'agit de la deuxième section du dossier.

Tooling

draw.io reste l'outil principal : bibliothèque ArchiMate via la recherche « ArchiMate », et bibliothèque BPMN déjà utilisée au Bloc 1. Archi, modeleur ArchiMate gratuit de The Open Group, est présenté comme optionnel et non requis.

Pitch CODIR

Le cours termine par un pitch de 90 secondes. Les questions proposées par le board sont révélatrices : « What would break first if legacy went down for a day? », « Who do I call if this map is wrong? », « Why should I trust this over the last one? ». La carte doit donc soutenir une conversation de responsabilité, de dépendance et de confiance — pas seulement prouver que le diagramme est syntaxiquement correct.

Bloc 2 · Key Takeaways

12 — Mémo express avant quiz

Architecture

  • DFD = data ; BPMN = process ; ArchiMate = structure.
  • ArchiMate : Business / Application / Technology.
  • Familles : Active structure / Behaviour / Passive structure.
  • Une vue utile relie les couches ; elle ne juxtapose pas trois inventaires.
  • Le board veut ownership + critical handoffs.

BPMN & gouvernance

  • Cloud et Legacy : deux pools dans le modèle raffiné.
  • Message flow = pointillé entre pools.
  • Parallel gateway = branches simultanées.
  • ITIL → CAB ; COBIT → APO03 ; TOGAF → enterprise architecture.
  • D2 = ArchiMate + refined BPMN + 2–3 labels ; aucun nouveau scope.
Transition vers le Bloc 3 : la carte montre maintenant la structure. La question ouverte du support devient : quels sont les actifs critiques, et existe-t-il seulement un registre pour les gérer ? Le Bloc 3 construira un registre de type CMDB à partir de ce qui a déjà été cartographié.
